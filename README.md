# SEMANTICS.md — 웨어러블 QA 벤치마크 의미론 명세

본 문서는 질문의 자연어 표현을 **어떤 데이터 구간에 대한 어떤 계산으로 해석할지**를 확정한다.
구현보다 명세가 먼저이며, 구현은 이 문서를 따른다. 문서와 구현이 어긋나면 문서가 옳다.

이 명세는 PHIA / PMData / LifeSnaps **세 벤치마크에 동일하게** 적용된다.

---

## 0. 용어

| 용어 | 뜻 |
|---|---|
| **표(table)** | 이름으로 등록된 하나의 시계열 테이블. 인덱스는 날짜. 예: `daily_metrics`, `exercise_entries` |
| **참조 표** | 한 문항의 정답 프로그램 문자열이 이름으로 언급하는 표들의 집합 |
| **기준일(today)** | 상대적 기간 표현을 실제 날짜로 바꿀 때 쓰는 앵커 날짜 |
| **정답 프로그램** | 질문에 대응하는 한 줄 파이썬 표현식. 실행 결과가 정답이다 |

---

## 1. 기준일 (today)

> **today = 그 문항의 정답 프로그램이 참조하는 표들의 최신일 중 가장 늦은 날**

```
today(code) = max{ last_day(T) : T ∈ 참조표(code) }
```

### 1.1 확정 사항

- `last_day(T)`는 **표 전체**의 최신일이다. `.query()` 등으로 걸러낸 뒤 남은 행의 최신일이 아니다.
  필터 후 최신일을 쓰면 "마지막 트레드밀 기록일"이 today가 되는 버그가 생긴다.
- 참조 표는 **실행 전에 정적으로** 확정한다. 실행 중에 누적하면 `during()` 호출 시점에
  아직 접근하지 않은 표가 빠져 호출 순서에 따라 답이 달라진다.
- 표를 하나만 참조하면 그 표의 최신일이 곧 today다.

### 1.2 예시 (PHIA 사용자 171: 요약표 10/31, 운동표 10/09)

| 정답 프로그램 | 참조 표 | today |
|---|---|---|
| `daily_metrics.during('last 14 days')['steps'].sum()` | {daily_metrics} | 10/31 |
| `exercise_entries.during('last 14 days')['duration'].sum()` | {exercise_entries} | **10/09** |
| `exercise_entries.on_days(daily_metrics.where('...'))['distance'].sum()` | {둘 다} | 10/31 (단 미사용, 2.3 참조) |

### 1.3 근거

질문은 특정 표에 대해 묻는다. "지난 14일간 운동을 몇 번 했나"는 운동 기록에 대한 질문이므로,
운동 기록이 존재하는 마지막 날을 기준으로 삼는다. 여러 표를 함께 보는 질문은 그중 가장 늦은
날을 쓴다 — 더 이른 날을 쓰면 늦게까지 기록된 표의 최근 데이터가 질문 범위에서 통째로 빠진다.

## 2. 기간 표현

기간 표현은 **문자열** 하나로만 주어지며 `during()`이 처리한다.

### 2.1 일 단위 — `last N days` / `past N days`

> **`[today − N, today − 1]`** — 어제부터 거슬러 올라가 **N일**. today는 포함하지 않는다.

```
today = 10/31,  last 14 days  →  10/17 ~ 10/30   (14일)
today = 10/31,  last 7 days   →  10/24 ~ 10/30   (7일)
today = 10/31,  last 1 days   →  10/30 ~ 10/30   (= yesterday)
```

- 구간 길이는 **정확히 N일**이다. 경계 양끝을 모두 포함해 N+1일을 보는 것은 오류다.
- `last 1 days`는 `yesterday`와 같은 날을 가리킨다. 의도된 귀결이다.
- 구간 안에 데이터가 없는 날이 있으면 그 날은 **건너뛴다** (4절 참조).

### 2.2 주 단위 — `last week` / `past week`

> **달력상 지난주.** 주는 **일요일에 시작해 토요일에 끝난다.**

```
today 가 속한 주의 일요일 = today − ((today.weekday() + 1) mod 7)
last week = [그 일요일 − 7일, 그 일요일 − 1일]
```

```
today = 2026-09-21(월)  →  last week = 2026-09-13(일) ~ 2026-09-19(토)
today = 2023-10-31(화)  →  last week = 2023-10-22(일) ~ 2023-10-28(토)
today = 2023-10-09(월)  →  last week = 2023-10-01(일) ~ 2023-10-07(토)
```

- **`last week` ≠ `last 7 days`.** 전자는 달력 경계에 맞춘 고정 구간이고, 후자는 today 기준
  이동 구간이다. 주 표현을 7일로 환산해서는 안 된다.
- `last N weeks`는 직전 N개 달력 주를 이어붙인 구간으로 정의한다.
  `[현재 주 일요일 − 7N, 현재 주 일요일 − 1]`

### 2.3 단일일 — `today` / `yesterday`

```
today      →  [today, today]
yesterday  →  [today − 1, today − 1]
```

### 2.4 절대 날짜

ISO 형식(`2023-10-15`) 문자열은 그 하루를 가리킨다. 기준일을 쓰지 않는다.

## 3. 조건부 표현

> **조건을 만족하는 날들의 집합**과 교집합을 취한다. 구간이 아니다.

조건부는 `during()`이 아니라 **`on_days()`** 가 처리한다. 기간과 조건은 의미가 다르므로
함수를 분리한다.

```python
# 기간 — 연속 구간. 기준일을 쓴다.
daily_metrics.during('last 14 days')['steps'].sum()

# 조건 — 날짜 집합. 기준일을 쓰지 않는다.
exercise_entries.on_days(daily_metrics.where('rem_sleep_percent > 30'))['distance'].sum()
```

### 3.1 `where(조건)` → 날짜 집합

조건을 만족하는 행들의 **날짜**를 반환한다. 컬럼 이름에 의존하지 않는다.

### 3.2 `on_days(날짜들)` → 부분집합

```
REM > 30% 인 날 = {10/03, 10/27}

on_days  →  10/03, 10/27 두 날만          ← 올바름
구간해석  →  10/03 ~ 10/27 전체 25일       ← 오류
```

### 3.3 기준일 비사용

`on_days()`는 날짜를 명시적으로 받으므로 기준일을 참조하지 않는다.
따라서 1절의 기준일 정책이 바뀌어도 조건부 문항의 답은 변하지 않는다.

## 4. 결측일과 유효일

### 4.1 결측일

구간 안에 행이 없는 날은 **건너뛴다**. 0으로 채우지 않는다.

```
last 14 days 구간에 실제로 12일치 행만 존재  →  12일치로 집계
```

각 문항은 실제 집계에 쓰인 **유효일 수**를 메타데이터로 기록한다.

### 4.2 유효일 기준 (PMData / LifeSnaps)

착용 시간이 짧은 날은 유효일로 보지 않는다. PHIA 합성 데이터에는 적용하지 않는다.

| 설정 | 기본값 | 민감도 분석 |
|---|---|---|
| `min_wear_minutes` | 600 (10시간) | 480 |

### 4.3 문항 제외

유효일이 부족하면 문항 자체를 생성 대상에서 제외한다.

```
유효일 수 < max(2, ceil(N × 0.5))  →  제외
표준편차·분산 문항은 유효일 ≥ 2 필수
```

제외된 문항은 **제외 로그**에 사유와 함께 전건 기록한다.

## 5. 답할 수 없는 문항 (NULL)

다음은 오류가 아니라 **정상적인 "답 없음"** 이며, 값 `0`과 구별한다.

| 상황 | 결과 |
|---|---|
| 조건을 만족하는 날이 하나도 없음 | `NULL` |
| 대상 기록이 하나도 없어 값을 꺼낼 수 없음 | `NULL` |
| 집계 결과가 `NaN` | `NULL` |
| **집계 대상 집합이 비었음** | **`NULL`** (개수 질문 제외, 아래) |

### 5.1 빈 집합의 집계 — 집계함수에 따라 갈리지 않게 한다

pandas 기본 동작은 일관성이 없다. 같은 "대상 없음"인데 답이 갈린다.

```
빈 집합.sum()    → 0      ← 데이터가 없는데 "0" 이라고 답하게 된다
빈 집합.mean()   → NaN
빈 집합.max()    → NaN
빈 집합.count()  → 0
```

그래서 규칙을 하나로 고정한다.

> **집계 대상이 빈 집합이면 `NULL`.**
> **단 개수를 묻는 집계(`count`, `nunique`, `size`, `shape`)는 `0`.**
> 빈 집합의 개수는 0으로 잘 정의되며, "몇 번 했나"의 답으로 0이 자연스럽다.

설정 키 `empty_set_policy` 로 전환한다.

| 값 | 동작 | PHIA 4,000행에서의 NULL 수 |
|---|---|---|
| `keep` | pandas 기본 (불일치 상태) | 102 |
| `no_data_only` | 기간 내 기록 자체가 없을 때만 NULL | 240 |
| **`null_except_count`** | **위 규칙 (기본값)** | **383** |
| `null_all` | 개수 질문도 NULL | 478 |

빈 집합의 원인은 둘로 구분해 기록한다.

| 원인 | 뜻 |
|---|---|
| `기간 내 기록 없음` | 그 기간에 원본 표 자체에 행이 없다 |
| `대상 없음` | 행은 있으나 앞선 필터(`query`)에 모두 걸러졌다 |

> **후속 과제 (PMData / LifeSnaps):** 이벤트 표(운동 세션, sRPE 세션)는 "기록 없음 = 발생
> 안 함"이므로 `sum` 도 `0` 이 타당하고, 일별 표(daily_metrics, stress_daily)는
> "기록 없음 = 측정 안 됨"이므로 `NULL` 이 타당하다. 표를 등록할 때 종류(`daily` /
> `event`)를 선언해 구분하는 안을 검토한다.

`0`은 "대상이 존재하며 그 합/개수가 0"인 경우에만 쓴다.

다음은 **문항 결함**이며 NULL이 아니라 제외 대상이다.

| 상황 | 처리 |
|---|---|
| 결과가 스칼라가 아님 (Series/DataFrame 반환) | 제외 |
| 실행 중 예외 발생 | 제외 |

## 6. 수치 정밀도와 채점

### 6.1 저장 정밀도

정규화 테이블은 **원본 정밀도를 유지**한다. 저장 단계에서 반올림하지 않는다.

> PHIA 공개 CSV는 값이 이미 소수 2자리로 반올림되어 있어, 여러 날을 합산하면 오차가 누적된다.
> 4,000문항 중 813건(20.6%)이 소수 둘째 자리에서 어긋난다. 같은 문제를 반복하지 않는다.

### 6.2 채점 기준

```
정답 판정:  |예측 − 정답|  <  0.011        소수 둘째 자리까지 같으면 정답
```

PHIA 원본 채점기는 `f'{v:.2f}'` 로 반올림한 뒤 **문자열을 완전 일치**시켰다. 취지는 같지만
반올림 경계에서 억울한 오답이 나온다.

```
정답 18.465   예측 18.47
  PHIA 컷 : '18.46' != '18.47'  ->  오답    (부동소수점 표현이 아래로 내림)
  본 기준 : 0.005 < 0.011       ->  정답
```

4,000문항에서 두 기준이 **64건** 갈리며, 그 64건은 전부 0.005~0.01 차이다. 계산 실패가
아니라 마지막 자리 표기 흔들림이므로 정답으로 본다. **0.02 이상 차이는 여전히 오답**이다.

- 범주형·날짜 답은 정규화 후 문자열 비교한다.
- `NULL`은 `NULL`끼리만 일치한다. `0`과 일치하지 않는다.
- 폭은 `grading.TOL` 한 곳에 있다.

### 6.3 답 추출

모델은 최종 답을 **지정된 형식**으로 제출한다. 자유 텍스트에서 첫 번째 숫자를 뽑는 방식은
사용하지 않는다 (질문에 포함된 기간 숫자가 답으로 잘못 추출된다).

## 7. 설정 스위치

`CONFIG`에는 **우리가 내린 결정**만 둔다. 기존 구현의 버그를 재현하는 스위치는 두지 않는다
(그것들은 `phia_legacy/`에 있다).

| 키 | 기본값 | 민감도 분석 값 | 근거 |
|---|---|---|---|
| `last_days_window` | `exclude_today` | `include_today` | §2.1 |
| `week_start` | `sun` | `mon` | §2.2 |
| `min_wear_minutes` | 600 | 480 | §4.2 |
| `null_on_empty` | `True` | — | §5 |
| `tol_abs` / `tol_rel` | 0.05 / 0.001 | — | §6.2 |

민감도 분석은 기본값과 대안값으로 벤치마크 전체를 재실행해 **모델 간 순위가 유지되는지**를
보고하는 방식으로 수행한다.

## 8. 불변식 (구현이 반드시 지켜야 할 것)

1. 같은 문항은 몇 번을 실행해도 같은 값을 낸다 (결정론).
2. 기준일은 실행 전에 확정되며 실행 중에 바뀌지 않는다.
3. `during()`은 문자열만 받는다. 날짜 집합을 받으면 오류를 낸다.
4. `on_days()`는 기준일을 참조하지 않는다.
5. 질문 문장과 정답 프로그램은 **하나의 템플릿에서 동시에** 생성된다.
   → 질문–코드 지표 불일치가 구조적으로 발생하지 않는다.
6. 전역 가변 상태를 두지 않는다. 모든 상태는 사용자 컨텍스트 객체에 담는다.
   → 여러 사용자를 동시에 처리해도 기준일이 섞이지 않는다.
